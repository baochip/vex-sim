# vex-sim

Containerized [Verilator](https://verilator.org/) simulation of the
baochip-1x **"bao" SoC**. Produces an FST waveform (`sim.fst`)
and captures the simulated DUART console to `console.log`.

Because the Baochip-1x is a large SoC, simulation models are broken up
into "views" of the chip. A view of the chip only contains the peripherals
relevant to a subsystem of interest. For example, an SCE simulation would
only include the SCE peripherals, but not the BIO. This is done to speed
up the simulation and also keep the waveform files manageable. Unused signals
are still simulated, polluting the waveform browser and simulation output
files.

See below for details on how to use `--view` to select a simulation view.

## Quick start

```sh
git submodule update --init --recursive   # populate baochip-1x (+ its deps)
./container-run                           # builds the image on first use
                                          # (~10 min toolchain), then the
                                          # sim model (first run: 21 s on a
                                          # 32-core host, scales with cores),
                                          # cached afterwards, then simulates
```

Outputs land in `./out/`:

- `sim.fst` — full waveform (open with `gtkwave sim.fst`, or any FST viewer)
- `console.log` — captured `[duart]` console output from the firmware

The simulation runs the firmware in `firmware/boot.bin` by default; a custom
firmware can be specified via the `--bios` argument. Simulation terminates
when `finisher.v` is signalled, or `VEXSIM_TIMEOUT` is reached.

Ctrl+C during a run should abort cleanly: the model stops, and the
partial waveform is still closed and saved to `out/sim.fst` (exit 130).
A second Ctrl+C leaves immediately, leaving `out/sim.fst` in a corrupt state.

The output of `sim.fst` can be viewed using the the [SCE variant]
(https://baochip.com/sce-surfer/) of the surfer waveform browser. Be sure
to upload both the .fst file and the .dis file that corresponds to the program
listing. The .dis file can be generated by running `objdump` on the ELF file
used to generate the `boot.bin` file (see the `--bios` argument below.).
[sce.surf.ron](./sce.surf.ron) is a template state file you can use for
stock copies of Surfer.

## Layout

```
vex-sim/
+-- baochip-1x/         # git submodule: the SoC + sim sources (mounted, not baked)
|   +-- verilate/       #   Litex build scripts (bao_soc.py, bao_core.py, ...)
|   +-- verilate/build/ #   model cache — persists here across runs
+-- golden/cram_axi.v   # golden core complex (fixed silicon; baked into image)
+-- lib/netlist/        # redacted gate-level VexRiscv netlist view (--netlist)
+-- firmware/boot.bin   # bundled default firmware (prebuilt nto-tests image)
+-- out/                # sim.fst, console.log, your own boot.bin
+-- patches/            # runtime patches (migen tracer py3.12, FST-close veril.cpp)
+-- Dockerfile          # toolchain image
+-- container-run       # wrapper (podman/docker)
```

The image carries the **fixed toolchain**: Verilator 5.052 (source build),
the Litex stack (migen + litex at the pinned baochip gitlink revs, tracer
fix applied) installed into a venv from git, and the **core complex**
(`cram_axi.v`, pulled in from the tape-out RTL). The
SoC "views" are NOT baked: the `baochip-1x` submodule tree is bind-mounted
read-write at `/opt/baochip-1x`, and the Verilator model builds INTO that
tree (per-view cache under `verilate/build/sim-<view>/`). The core variant
(RTL vs `--netlist`) is part of the cache key: `sim-<view>-netlist/`, so
switching variants triggers exactly one re-verification and each variant
then stays cached (flipping back rebuilds once again).

As a result, the simulation behaves as follows as files are changed:
- edit any SoC-level RTL / build script under `baochip-1x/` and rerun — no
  image rebuild; the model build re-verilates automatically,
- the model cache (`baochip-1x/verilate/build/`) survives between runs and
  lives with your checkout (~900 MB; `make distclean` removes it),
- starting a container is instant: no per-launch pip install, and the core
  complex is installed from the golden artifact instead of regenerated
  (~2 min of `bao_core.py` skipped),
- dev overrides: `VEXSIM_FORCE_PREP=1` reinstalls litex/migen from the
  mounted `deps/` forks (editing the forks without image rebuilds);
  `VEXSIM_BUILD_CORE=1` regenerates `cram_axi.v` from the mounted RTL tree.

## Views (SoC definition)

`--view` selects which SoC definition builds the model (each view caches its
own model under `verilate/build/sim-<view>/`):

| `--view` | builds | status |
|---|---|---|
| `bao_soc.py` (default) | main bao SoC + BIO | working |
| `bao_sce.py` | SCE/crypto variant (`bao_soc.py --sce`) | working |
| `bao_udma.py` | UDMA variant (`bao_soc.py --udma`) |**WIP** - needs further porting from the full SOC environment to the OSS environment. Not ready for use yet. |


```sh
./container-run --view bao_sce.py build    # build + run the SCE model
./container-run --view bao_sce.py --bios out/fw-hash.bin   # SCE KAT image
```

Firmware must match the view's peripheral map (images are linked for a
topology): the SCE view keeps only duart/sce/testbench, so run SCE KAT
images there (e.g. `out/fw-hash.bin`: `~~Primordial up!~~` → `sce_hash`
KATs). Full-chip images (`xous-core`, etc.) need
the default view; on the SCE view they may fault on a missing peripheral and
reset-loop (`hello world!` / `booting... 001`) forever.

## Core view: RTL vs redacted netlist (`--netlist`)

By default the CPU core complex (`cram_axi`) simulates from the
tape-out **RTL** (golden `cram_axi.v`). `--netlist` swaps the core for the
redacted **gate-level netlist**: the taped-out VexRiscv complex minus the
CM7 (absent from this hierarchy), standard cells replaced by behavioral RTL
models, RAM macros by open-source behavioral models:

```sh
./container-run --netlist            # build + run the netlist-core model
```

All netlist-view files live in [`lib/netlist/`](lib/netlist/) (open-source /
redistributed-safe; regenerate the wrapper with
`lib/netlist/README.md`'s command). The netlist top carries exactly the
golden core's 156 scalar ports via a generated wrapper, so the SoC build
(`sim.v`) is bit-identical between views; only the core implementation
changes. The model cache is keyed per variant (`sim-<view>-netlist/`), so
RTL ⇄ netlist switches re-verify exactly once each, in every view
(`bao_sce.py` / `bao_udma.py` included).

Each cached model carries a `.vexsim-core` provenance stamp; a model verilated
from the other core (or predating the stamp) is rebuilt automatically.

Notes:
- Waveforms: only the **core subtree** is obfuscated (`cram_axi` internals
  = `_*`/`U*_` nets, `CLKCELL_BUF*` cells, `_*_1kx32` RAM macros); the
  surrounding SoC (crossbars, duart, sce, ...) keeps its structured RTL names.
- `bios` mode (firmware swap) works in both views (same flow: init-file
  swap into the matching cached model dir).
- Gate-level sim runs much slower than the RTL model. You may need to raise
  `VEXSIM_TIMEOUT` for long firmware runs.
- The netlist's `test_*`/scan/DFT inputs are tied off; `stov`-style test
  modes are unreachable (the silicon ties them with TIEL cells).

## Options

| Env var | Default | Meaning |
|---|---|---|
| `VEXSIM_VIEW` | `bao_soc.py` | SoC definition (see table) |
| `VEXSIM_NETLIST` | — | `1` (= `--netlist`): simulate the redacted gate-level core from `lib/netlist/` instead of RTL; model cache is keyed per core variant |
| `VEXSIM_NETLIST_DIR` | `/opt/vexsim-lib/netlist` | netlist staging dir inside the container (override for host/native runs: point at your `vex-sim/lib/netlist`) |
| `VEXSIM_TIMEOUT` | `1800` | wall-clock cap (s) on the simulation run |
| `VEXSIM_BIOS` | `/opt/firmware/boot.bin` | firmware image (`bios` mode) |
| `VEXSIM_THREADS` | `5` | Verilator `--threads` (model build) |
| `VEXSIM_JOBS` | `20` | C++ compile parallelism (model build) |
| `VEXSIM_TRACE_START/END` | `0` / `200000000000` | trace window (ps) |
| `VEXSIM_CPUS` | — | pass `--cpus` to the engine |
| `VEXSIM_DEBUG` | — | `1`: `set -x` command tracing inside the entrypoint (every startup step, timestamped) |
| `VEXSIM_FORCE_PREP` | — | `1`: reinstall litex/migen from the mounted `baochip-1x/deps/` forks (dev flow: editing the forks without image rebuilds) |
| `VEXSIM_BUILD_CORE` | — | `1`: regenerate the core complex (`bao_core.py`) from the mounted RTL instead of using the golden `cram_axi.v` |
| `VEXSIM_NETWORK` | `none` | container network for the run (sim needs none; set `slirp`/`bridge` only if extending the flow to need net) |
| `VEXSIM_BUILD_ISOLATION` | — | e.g. `chroot` — image builds on rootless podman hosts without a systemd user session (runc can't create cgroup scopes there; only `podman build` is affected, `podman run` works) |
| `CONTAINER_ENGINE` | auto | `podman` or `docker` |

```sh
./container-run --rebuild          # rebuild the image after editing Dockerfile
./container-run build              # force model re-verification/build
./container-run bash              # shell inside the image
VEXSIM_TIMEOUT=600 ./container-run
```

## Firmware

The image bundles a prebuilt `boot.bin` that performs a "smoke test" on
the build, including a sim early-quit hook so runs end at `$finish` in
seconds. To run your own firmware, build it
(anywhere with rust + riscv-none-elf binutils; the submodule has the
sources):

```sh
./container-run bios /path/to/boot.bin
./container-run --bios /path/to/boot.bin --view bao_sce.py
```

## Native (no container)

The image merely automates what these host tools do; if you have them all
(Verilator 5.052, the Litex fork venv, rust + riscv-none-elf binutils):

```sh
cd baochip-1x/verilate
./verilate.sh                      # testbench target; see script for variants
```

## Known limitations

- `bao_udma.py` view: broken in the pinned sources (the `soc_oss/rtl`,
  `soc_oss_tapeout`, and `candidate` RTL trees referenced by
  `deps/soc_oss/udma_adapter.py` are absent from the submodule). The one
  bug that *was* fixable there — the same parenless `ahbs` interface
  variable — is fixed in `soc_ifsub_udma.sv`, but the missing trees block
  the view until they are published.
- `verilate.sh -t xous` (Xous OS boot simulation) is **not** wired into the
  container yet. Follow-on work: `cargo xtask bao1x-sim` + `finisher.v`
  Xous define.
- Image build needs network (apt, pip git wheels, Verilator tarball). The
  simulation itself never touches the network.
- The DUT is the full SoC; a full trace is large (15 MB after early quit;
  multi-GB at the 1800 s timeout). `VEXSIM_TRACE_START/END` trim the window.

## Implementation Notes

Exact tool revisions in `VERSIONS`. Two patches make the flow work (see
`patches/`, never committed to the submodule): a migen bytecode-tracer fix
for Python 3.12, baked into the image's migen at build time; and a
replacement litex `veril.cpp` that closes the FST writer via `atexit` +
SIGTERM/SIGINT/SIGHUP, re-applied to the venv at every container start -
upstream never calls `Writer::close()`, so wave files would lack their
header/hierarchy/seek tables after `$finish` or a timeout kill.
